# 경기 확장 최종 설계 검토 — 변경 최소화

검토일: 2026-10-27. iOS `62d85b4ab384b61c4827ed9b44a9c7ea786568f2`의 실제 코드와 이 브랜치의 서버를 기준으로 검토했다. 이 문서는 구현 결과가 아니라 **최소 변경을 위한 권고 설계**다. 이전 인계 문서의 광범위한 모델·저장소 개편보다 이 문서의 초기 범위를 우선한다.

## 1. 결론과 범위

**서울 형식의 경기 정류소 파일 하나와 앱 내부 GBIS adapter를 추가한다. 기존 백엔드 API·서버 코드·서울 ID·CoreData 모델은 유지한다.**

초기 지원 권고는 경기 정류소 검색, 주변 지도, 최근 검색, 실시간 도착 조회다. **경기 즐겨찾기·정기알림·위젯 저장은 후속으로 미룬다는 전제**에서 변경을 최소화했다. 사용자가 이 기능들을 영구 제외하라고 요청한 것은 아니다. 동시 출시가 필요하면 아래 후속 범위를 함께 설계해야 하며, 이를 데이터 변환만으로 해결했다고 볼 수 없다. 서울의 기존 기능은 유지한다.

| 영역 | 초기 설계 | 제외할 과한 변경 |
|---|---|---|
| 정적 데이터 | 서울 레코드 형식으로 경기 파일 1개 추가 | 경기 전용 정적 DTO, 서울 원본 교체 |
| 앱 식별 | 기존 String 전달 유지, 신규 경기 키만 `gg:` 접두사 | 서울 키 전체 변경, 모든 인터페이스에 provider 인자 추가 |
| 실시간 | 기존 repository 안에서 제공자별 endpoint/DTO 선택 | 서버 프록시, 서울 응답 DTO 구조 개편 |
| 지도 | 숫자 클러스터 키와 원래 문자열 키 연결 | 지도 SDK 교체, ID 길이로 제공자 추정 |
| 저장 | 최근 검색만 이전 값 호환; 경기 즐겨찾기 저장 차단 | CoreData 모델 버전 증가, 서울 즐겨찾기 재작성 |
| 백엔드 | 변경 없음 | 기존 `/regular` 확장, 기존 collection에 경기 저장 |
| 부가 정보 | 응답에서 제공하는 노선명·행선지 사용 | 전체 노선 방문 파일 상시 로드, SQLite 도입 |

## 2. 정적 파일 — 기존 DTO 재사용

앱 리소스 후보 이름은 `bus_station_list_gyeonggi.json`. 기존 서울 `bus_station_list.json`은 그대로 둔다. 루트는 `DESCRIPTION`, `REGION="경기"`, `DATA`, 행은 기존 서울 필드명과 타입을 쓴다. `BusStopListDTO`의 지역 enum과 `toDomain` 분기만 확장하고 별도 정적 레코드 DTO는 만들지 않는다.

변환 규칙은 [형식 검증 문서](SEOUL_FORMAT_COMPATIBILITY.md)를 따른다. `stationId → node_id`, `mobileNo → stop_no`, 좌표는 문자열, `nxtStn=null`. 미정차 이름을 제외한 38,778건이 대상이다. `stop_no`에 stationId를 대신 넣지 않는다.

현재 운영용 export 명령과 앱 리소스 반영은 미구현이다. 후속 데이터 작업은 기존 `collect.py`에 서울 형식 export 단계를 추가하고 기존 스냅샷에서 재현 가능하게 만드는 정도면 된다. 수집기를 다시 만들 필요는 없다. 생성 파일과 원본 스냅샷 버전·해시를 연결한다.

`stations.json`, `routes.json`, `route_stations.json`은 저장소의 정규화 원본/검증 자료로 유지한다. **초기 앱 번들에는 변환 정류소 파일만 넣는다.** 정적 노선/방문 데이터가 없어도 실시간 목록 응답으로 노선명·방문 순번·행선지를 얻을 수 있다. 다음 정차 정류소 표시가 필요해질 때만 보조 데이터를 추가한다.

## 3. ID — 서울 값과 기존 함수 시그니처 보존

현재 앱은 `busStopId: String`을 검색 → coordinator → `ArrivalInfoRequest` → repository로 전달한다. 이 흐름을 유지하고 **문자열은 앱 내부 정류소 키**로 정의한다.

| 구분 | 파일 값 | 앱 내부 busStopId | 화면 번호 | 외부 API 파라미터 |
|---|---|---|---|---|
| 서울 | stop_no=`01001` | `01001` 그대로 | `01001` | arsId=`01001` |
| 경기 | node_id=`200000078`, stop_no=`01109` | `gg:200000078` | `01109` | stationId=`200000078` |

접두사는 새 경기 키에만 추가한다. 원본 JSON의 node_id나 API 파라미터에 붙이지 않는다. 지역은 행정구역이 아닌 API 제공자다. 서울 소재 GBIS 정류소도 `gg:100000001`로 별도 유지한다.

키 생성/해석은 공통 작은 helper 한 곳에서 수행한다. 경기 접두사 제거와 비어 있지 않은 숫자 stationId 검증, 기존 서울 ID 처리를 담당한다. 잘못된 `gg:` 키나 알 수 없는 접두사는 오류로 처리하며 서울 조회로 fallback하지 않는다. ID 길이·좌표·이름·표시번호로 제공자를 추정하지 않는다. 기존 서울 호출은 기존 arsId를 그대로 전달한다.

`fetchArrivalList(busStopId: String)`, coordinator의 String 인자, 서울 즐겨찾기 identifier 형식은 유지할 수 있다. 각 화면에서 직접 prefix를 분해하지 않는다. 향후 타입 안전성이 필요할 때 typed reference를 도입할 수 있지만 초기 출시 필수는 아니다.

### 표시번호와 최근 검색

`BusStopInfoResponse`와 정류소 도착 응답에 optional `displayNumber`를 추가한다. 기존 생성자 기본값은 nil. 서울은 nil이면 기존 busStopId를 표시하고, 경기는 변환 파일의 stop_no를 전달한다. 경기 번호가 없으면 **빈 문자열**로 전달하고 내부 키를 표시하지 않는다. UI helper는 잘못된 경기 데이터에서도 내부 ID로 fallback하지 않는다.

검색의 번호 비교·정렬·강조, 검색 셀, 지도 설명, 도착 화면 헤더는 표시번호를 사용한다. 선택·조회는 내부 키를 사용한다. `nxtStn=null`이면 방향 문구와 구분자도 생략한다. provider 배지로 서울/경기 조회 목록을 구별한다. 동일 물리 정류소를 자동 병합하지 않는다.

최근 검색은 CoreData가 아니라 `UserDefaults`의 `[BusStopInfoResponse]` JSON이다. 새 optional 필드는 이전 JSON에서 없어도 읽혀야 한다. 새 키 `recentSearchesV2`에 저장하고, 키 자체가 없을 때만 기존 `recentSearches`를 읽어 초기화한다. 기존 키는 보존한다. 사용자가 비운 빈 배열도 새 키에 저장해 이전 목록이 다시 살아나지 않게 한다. 경기 기록이 구버전 앱의 서울 조회로 들어가지 않도록 두 저장 키를 분리한다. 최대 5건 정책은 유지한다.

### 지도

현재 `NearMapViewController`는 `Int(response.busStopId)`를 만들고 `LeafMarkerUpdater`는 숫자를 5자리 문자열로 복원한다. 접두사만 추가하면 경기 마커가 누락되므로 이 두 경계는 수정 필수다.

클러스터의 숫자 identifier는 지도 수명 동안 유일한 임시 값으로 두고 원래 내부 키를 별도 보관한다. `BusStopClusteringKey`에 문자열 키를 추가해 copy 시에도 보존하거나 동일 수명의 역매핑을 둘 수 있다. **선택 이벤트는 보관한 원래 키**를 내보낸다. hashValue를 유일한 ID로 쓰거나 접두사를 지운 숫자를 다시 서울 번호로 복원하지 않는다. 재조회 시 선택된 정류소의 내부 키로 마커를 복원한다.

## 4. 실시간 adapter — 기존 화면 모델을 최대한 재사용

`DefaultBusStopArrivalInfoRepository`에서 내부 키를 해석한다. 서울은 기존 endpoint/DTO/변환 경로를 그대로 호출한다. 경기만 새 GBIS endpoint/DTO를 통해 기존 화면 응답으로 변환한다. 외부 응답의 envelope가 다르므로 **실시간 DTO는 별도로 필요**하다.

초기 요청은 `getBusArrivalListv2(stationId)` 하나로 충분하다. 개별 노선 반복 호출과 `getBusArrivalItemv2` 통합은 초기 필수가 아니다. API 상세·실호출 근거는 [인계 문서 4절](APP_HANDOFF.md#4-실시간-도착-요청-및-파싱)을 따른다.

최소 도메인 추가:

- 정류소 도착 응답의 busStopId는 요청 때의 `gg:...`를 유지한다. 표시번호·정류소명은 로드한 정적 사전에서 가져온다. 빈 도착 목록에서도 헤더와 지도 이동이 가능해야 한다. 변환 후 복사 함수들도 displayNumber를 보존한다.
- `BusArrivalInfoResponse`에 optional `staOrder`(서울 기본 nil)를 추가하고 복사·시간 갱신에서도 유지한다. 경기 행은 `(stationKey, routeId, staOrder)`로 구분한다. 같은 노선의 반복 방문을 합치지 않는다. 순번이 없으면 목록 행은 남기되 특정 방문 대상 동작은 제공하지 않는다.
- `ArrivalState.unknown`을 추가해 ETA 누락을 “도착정보 없음”으로 표시한다. `replaceTime`과 관련 switch도 확장한다. 기존 서울 상태 변환은 유지한다. 빈 ETA를 0초/곧 도착/운행종료로 만들지 않는다.
- GBIS 유형 코드는 DTO에 원문 보존한다. 초기 화면에서는 검증된 유형만 기존 표시 enum에 명시적으로 매핑하고, 미매핑 값은 기존 `.common` 일반 표시로 보낸다. 원문 `11/13/50`을 서울 enum rawValue에 직접 넣지 않는다. 유형 enum 전체 재설계는 필요 없다.
- `routeDestName`은 행선지 텍스트로만 표시한다. 다음 정차 정류소가 아니므로 `nextStation`은 정보가 없으면 빈 문자열. 그 경우 “방면” 같은 빈 정보용 문구도 생략한다.
- 정적 노선에 없는 동적 버스도 표시한다. HTTP/인증 오류, 정상 빈 목록, ETA 없음, 운행 종료를 구분한다. 숫자/문자열 혼재와 초·분 단위는 adapter 안에서 처리한다.

이 변경은 기존 화면 재사용을 위한 제한적인 확장이다. 새 경기 전용 전체 화면 계층이나 공통 provider 프레임워크는 만들지 않는다.

## 5. 저장·알림 경계 — 차단 위치까지 필요

즐겨찾기/알림을 후속으로 미루면서 버튼만 숨기면 충분하지 않다. 기존 앱에는 알림 추가 흐름에서 검색·지도·최근 검색으로 정류소를 선택하는 경로가 있다.

1. 일반 검색/지도에서는 경기 조회를 허용하되 경기 즐겨찾기·정기알림 동작을 비활성화하고 미지원 상태를 표시한다.
2. 알림 정류소 선택 흐름에서는 경기 검색 결과·최근 검색·주변 추천·지도 선택을 제외하거나 선택을 거부한다. 서울 선택 흐름은 유지한다.
3. `DefaultBusStopUseCase.handleFavorites`와 알림 선택 `update` 경계에서도 경기 키를 거부한다. 실패 시 ViewModel은 알림 선택 완료로 화면을 닫지 않는다. UI를 우회해도 기존 즐겨찾기/CoreData/RegularAlarmEditingService에 경기 ID가 전달되지 않아야 한다.
4. 기존 서버 API에는 원래 서울 데이터만 전달한다. 서버 sync, 서울 alarm id, CoreData, 기존 위젯/App Group 저장 스키마는 수정하지 않는다. 새로운 `.unknown` 상태나 경기 응답도 기존 위젯 저장 경로에 넣지 않는다.

경기 즐겨찾기를 함께 출시하려면 stationId+routeId+staOrder의 보존, 화면 matching, 저장 형식, 재조회까지 추가 설계가 필요하다. 경기 정기알림은 [백엔드 후속 계획](../../docs/superpowers/plans/2026-10-12-gyeonggi-backend.md)의 신규 endpoint·별도 collection으로만 진행한다. 이 확장을 초기 필수 작업으로 간주하지 않는다.

## 6. 후속 구현 순서와 완료 기준

1. 서울 형식 export와 enum/번들 로드. 경기 로드 실패가 서울 데이터를 막지 않게 한다.
2. 키 helper, 표시번호, 최근 검색 이전 값 읽기, 검색/지도 연결. 지역별 검색 결과를 모두 `.seoul`로 감싸는 기존 코드도 수정한다.
3. GBIS endpoint/DTO/adapter, 제한적인 도메인 확장, 경기 저장·알림 경계 차단.
4. 앱 빌드·실기기 회귀 검증 후 기능 활성화. 수집 데이터는 2026-10-11 스냅샷이므로 출시 전에 새 스냅샷과 승인된 API 호출량도 확인한다.

검증할 핵심 사례:

- 서울 `01001`의 검색·조회·즐겨찾기·알림·최근 검색 값이 그대로 유지된다. 기존 서버 소스 diff는 0이다.
- 경기 `01109` 검색 → `gg:200000078` 선택 → API `stationId=200000078` → 화면 `01109` 표시가 이어진다. 접두사가 외부 API로 나가지 않는다.
- 같은 mobileNo를 가진 서로 다른 stationId, 번호 없는 271건, 서울/경기 중복 물리 정류소가 별도 키로 유지된다. `gg:` 키가 UI 번호로 노출되지 않는다.
- 지도 재조회·선택·상세에서 지도 복귀 시 원래 문자열 키가 유지된다. 경기 마커가 Int 변환 실패로 사라지지 않는다.
- 기존 최근 검색을 읽고 새 경기 기록도 앱 재시작 뒤 복원한다. 새 목록 비우기 후 구 목록이 다시 복원되지 않는다. 기존 저장 키는 바뀌지 않는다.
- 반복 방문 staOrder, 가변 routeName, ETA 없음, 미매핑 유형, 빈 목록, 인증 오류, 정적 파일 밖 노선을 fixture로 확인한다.
- 알림 추가 흐름의 검색/최근 검색/지도와 직접 use case 호출 모두 경기 저장을 차단한다. 기존 서버 요청 및 CoreData에 경기 ID가 0건이다.
- 실기기에서 약 8.7 MB의 경기 JSON 추가에 따른 로딩·메모리·검색/지도 응답 시간을 측정한다. 성능 문제가 측정될 때 인덱싱을 보강하고 SQLite는 선행 도입하지 않는다.

현재 확인한 것은 원본 코드의 변경 지점과 JSON 형식/디코딩 가능성이다. iOS 통합 코드·전체 빌드·실기기 성능은 아직 검증하지 않았다.
